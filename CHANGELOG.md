Dates are in ISO 8601 (YYYY-MM-DD). Entries are grouped by release milestone.

## [Unreleased]

### Changed
- **The documented Nginx config used `listen ... ssl http2`, deprecated since Nginx 1.25.1**, which warns on every reload. It now uses the separate `http2 on;` directive. Carefully, though: on older Nginx that directive does not exist and the server **refuses to start**, which is a worse failure than the warning it replaces — and Ubuntu 24.04 LTS still ships 1.24. The config carries an inline note giving the old form for those versions, and Prerequisites now states the 1.25.1 requirement, since no Nginx version was pinned there before.

### Fixed
- **Static assets were served with no `Cache-Control` header at all, so a deploy did not reliably reach anyone.** Neither the documented nginx config nor `public/.htaccess` set any cache policy, which leaves browsers on *heuristic* caching — roughly 10% of the file's age — replaying a stale copy without revalidating. v1.7.2 shipped a rewritten Feeding Frenzy soundtrack that returning players would simply not have heard, and the release notes could only document that rather than fix it. The two directories need opposite policies, which is why one rule would not have done. `/build/` is Vite output with **content-hashed filenames** (`app-D0CG0Rrn.js`), so a changed file is a different URL and the old one can never be wrongly reused — it gets `max-age=31536000, immutable`, which is also a straight performance win it was never getting. `/games/` is the easter-egg bundle with **stable filenames** (`orca-music.js`), so the same URL must return new bytes after a deploy — it gets `no-cache`, which means *revalidate before use*, not *do not store*; the server already sends `ETag`, so that costs a 304 rather than a re-download. Both server options are covered, since `DEPLOYMENT.md` offers nginx or Apache: location blocks for the former, `mod_setenvif` + `mod_headers` for the latter, each wrapped in `<IfModule>` so a missing module degrades instead of 500ing. One nginx trap is called out in a comment where someone will hit it: `add_header` is inherited from the server block **only** when a location declares none of its own, so both new blocks repeat the three security headers — without that, these paths would silently lose `nosniff` and `X-Frame-Options`, which matter most on exactly the JS they serve. The documented server block was extracted and run through `nginx -t` rather than eyeballed.

## [v1.7.2] — 2026-08 — Whitefin

### Notes for upgrading from v1.7.1 Remora
- **Nothing here needs a maintenance window.** There are **no migrations** — unlike v1.7.1,
  which had three and wanted one. No `php artisan migrate`, no `db:verify-schema` run, and no
  changes under `app/`, `routes/` or `config/` at all. The whole release is two dependency
  bumps, a static easter-egg bundle in `public/games/`, and docs.
- **`composer install`** picks up `league/commonmark` 2.9.0. Lock only — no constraint moved.
- **`npm ci && npm run build` is required, not optional.** `pdfjs-dist` went 5 → 6, a major
  version, Vite bundles it, and `public/build` is gitignored — so the new worker chunk exists
  only after a build. Building needs **Node ≥ 22.13**, which pdfjs v6 requires; CI pins
  `node-version: '22'`, which satisfies it.
- **`composer install` alone does not close the vulnerability this release exists for.** That
  is the one thing here that can bite. GHSA-hq66-cqwq-w95j is *client-side*: it fires when a
  browser opens a malicious PDF through `thumbnail-generator.js` or `asset-editor.js`. Until
  the assets are rebuilt **and served**, users are still running the vulnerable renderer, no
  matter what `composer audit` says. A deploy that treats a security release as a PHP job
  will report clean and remain exposed.
- **Returning players will keep the old easter egg.** `public/games/**` is served with **no
  `Cache-Control` header at all**, so browsers fall back to heuristic caching and happily
  replay a stale `orca-music.js`, `orca-game.js` or `shark.svg` without revalidating. This
  release does not change that. A hard reload or a CDN purge is the workaround; adding cache
  headers to the static bundle is the real fix and is deliberately out of scope here. Worth
  knowing before "the new soundtrack didn't ship" arrives as a bug report.
- **No spec versions moved**, so in-flight branches can merge normally rather than rebase —
  the opposite of v1.7.1, where twelve moved. The only `specs/` change is a one-line
  `pdfjs-dist` version comment in `architecture.md`, caught by `spec-lint`'s manifest
  cross-check rather than by review.
- **`PDFDocumentProxy.destroy()` no longer exists** in pdfjs v6. Nothing in `resources/js/`
  ever called it, so nothing broke here, but any in-flight branch adding PDF cleanup code
  needs to know before it rebases onto this.

### Changed
- **The Feeding Frenzy shark is redrawn, and its jaw now hinges on its jaw rather than on its eye.** The chomp had never worked: `shark.svg` carried `viewBox="0 -8 110 52"` — a *negative* `min-y` — while the CSS pivoted the lower jaw at `transform-origin: 18px 23px`. Under `transform-box: view-box`, the browser default for an SVG child, those pixels resolve against the viewBox origin, so the real pivot was user-space **(18, 15)**: the eye socket. The jaw was swinging around the shark's face, which is the kind of bug that looks like bad artwork rather than a wrong number, and is why it read as "the shark doesn't look good" instead of as a broken animation. The new `viewBox` is `0 0 120 52`, matching the `.game-shark` box exactly, so one user unit is one pixel and the pivot is now literal — and the artwork stops being letterboxed, which the old 2.115 aspect inside a 2.31 box had been costing it about five pixels of dead space on each side. Three things in the redraw are load-bearing rather than decorative, and each is commented where it lives. The mouth is a **notch cut out of the body** — the body path's front-bottom edge stops at the upper jaw line and the cavity plus hinged chin fill the gap — because the obvious alternative, a complete body silhouette with a jaw drawn on top, gives the shark a second chin the moment the jaw drops. Neither the body nor the chin strokes its throat edge: both are a fill plus a separate *open* outline path, since a closed stroked path draws a seam right where the two meet and the chin then reads as a slab pasted onto the head. And the gape is capped at **16°** by geometry, not taste: a static cavity is only hidden when closed if the chin is thicker than `r·sin(gape)`, so widening the bite means fattening the chin, which is recorded next to the keyframes so the next person to reach for a bigger number knows what else has to move. The teeth needed one non-obvious fix — white teeth on a cream chin are nearly the same value and dissolved into a pale smear at the size the shark is actually drawn, so a dark gum band sits behind the lower row and they read as white-on-dark. Colours stay in the cold blue-grey the game uses to mean *threat* (warm means food), pushed to higher contrast because `#orca-game-area` desaturates the whole scene by 65% and the old belly washed out under it; they are also kept clear of the gold fish's palette, since `colorizeFish()` recolours by naive string replacement over the raw SVG text and a shared hex would repaint the shark. Finally, sharks spawn in packs and shared one animation clock, so a pack bit in perfect unison — each now gets a random negative `animation-delay`, which starts it mid-cycle. **None of this is covered by anything:** the spec puts the client game bundle outside its contract, no browser test touches the game, and the visuals were checked by screenshotting the real `spawnShark()` output against the running app.
- **Feeding Frenzy's soundtrack has a real melody now, and shark attacks get their own music.** The old lead was one rhythmic idea repeated — every bar the same off-beat eighths, ~8 notes wall to wall, never dropping below B4, and a bug that accented ~90% of notes, which is the same as accenting none. It is now a 16-bar clavinet tune in A A′ B A″ form with composed per-bar dynamics, roughly half the note density, and a soft chord pad underneath. The wah that made it grate (`Q = 7`, peaking at 2.1 kHz — dead centre of where the ear is most sensitive) is tamed, and `clavNote()` rolls the sawtooth back as pitch rises, which is what makes the high notes usable rather than stabby. The lead also reacts to threats on screen, where before it noodled cheerfully straight through a shark attack: at 1–2 threats it thins to its skeleton, at 3+ it hands over to an 8-bar 70s chase riff on overdriven wah guitar with chord stabs on the off-beats. That riff is deliberately sparse — 64% of its steps silent — and never repeats exactly: its ornaments carry probabilities and alternate pitches (~10¹¹ realisations of the cycle) while its identity notes stay fixed, so it keeps evolving without losing the tune. The bassline everyone liked is untouched, byte-for-byte, in all three states. Audition the lot at `public/games/music-lab.html`.

### Fixed
- **Starting Feeding Frenzy quickly enough played the whole round in silence.** The music module is injected with no `onload`, and both the boot and start calls no-op when `window.OrcaMusic` is missing — deliberately, so the game survives the audio failing to load, but between them they turned a *late* module into an absent one with no error anywhere. Beating the script to the instructions overlay was enough to trigger it. The loader now picks the music up when it actually lands; autoplay policy is satisfied because the keypress already gave the page sticky user activation.

### Security
- **`pdfjs-dist` 6.2.108 closes a high-severity arbitrary-JavaScript-execution hole (GHSA-hq66-cqwq-w95j), up from 5.7.284.** Unlike most advisory noise this one was **genuinely reachable**: the app renders user-uploaded PDFs client-side in `thumbnail-generator.js` and `asset-editor.js`, which is exactly the “opening a malicious PDF” path the advisory describes, and a DAM takes PDFs from anyone who can upload. No patched 5.x exists — that line ended at the vulnerable release — so the only fix is the major bump, which is why this changes a `package.json` constraint rather than nudging a lockfile. The upgrade was verified rather than assumed, a major version of a rendering library being exactly where things break quietly: the app touches seven pdfjs APIs (`GlobalWorkerOptions`, `getDocument`, `numPages`, `getPage`, `getViewport`, `render`, and the `build/pdf.worker.mjs` worker path), and all seven were exercised against a generated PDF under both versions — identical page count, identical viewport (612×792), identical scaled thumbnail geometry (320×414), identical extracted text. The one step Node cannot reach, `render()` to a real canvas, was then driven in headless Chromium against both versions and came out **pixel-identical**: same 320×414 canvas, same 273 ink pixels, same 3031-byte JPEG data URL, no page errors. That check earned its keep, because the E2E suite names PDFs only as seeded filenames and never rasterises one — nothing in CI would have caught a rendering regression. The probe did surface one real removal, `PDFDocumentProxy.destroy()`, gone in v6 — harmless here only because nothing in `resources/js/` ever called it, and worth knowing before anyone adds cleanup code. v6 requires Node ≥ 22.13; CI pins `node-version: '22'`.
- **`league/commonmark` 2.8.3 → 2.9.0, clearing six advisories.** It is a transitive dependency of `laravel/framework` (`^2.8.1`) and `laravel-lang/publisher` (`^2.4.1`), both of whose constraints already allowed 2.9.0, so this is a lock bump with no constraint change and nothing else moving. **None of the six was reachable here.** Five are denial of service via crafted Markdown, and the only two call sites — `AboutController::index()` and `SystemController::documentation()` — convert repo-owned files behind a fixed eight-name allowlist, so attacker-supplied Markdown never reaches the parser. The sixth is an `AttributesExtension` `href`/`src` filter bypass, and `GithubFlavoredMarkdownConverter` does not load that extension. Taken anyway because `composer audit --locked` is a CI gate (`tests.yml`) and was failing every build from the moment the advisories landed. Rendered output is byte-identical across all nine documents the app can serve, verified by hashing 2.8.3's HTML against 2.9.0's rather than assuming a patch release is inert.

## [v1.7.1] — 2026-08 — Remora

### Notes for upgrading from v1.7.0 Sucker Fish
- **This release has migrations, unlike v1.7.0.** Three of them:
  `2026_08_06_100000_add_s3_key_hash_to_assets_table`,
  `2026_08_06_100001_widen_s3_key_columns_on_assets_table` and
  `2026_08_06_110000_widen_filename_columns`. Run `php artisan migrate --force`.
- **Run the widening migration in a maintenance window.** MySQL/MariaDB DDL is not
  transactional, and `..._widen_s3_key_columns...` drops two indexes on `assets`, widens five
  columns and recreates the indexes at a 255-character prefix. If it dies between the drops and
  the recreations, `assets` is left wide and **unindexed** — recovery is re-running the two
  `DB::statement()` index creations at the end of that migration's `createS3KeyIndexes()`. The
  column widening itself is `ALGORITHM=INPLACE` (extending a `varchar` whose length-byte count
  does not change), so it does not copy the table; the backfill in the first migration is the
  only slow step, and it is isolated there precisely so a retry never repeats it.
- **Then run `php artisan db:verify-schema`.** New command, and the only check that the schema
  the migrations produced is the one the application believes in — the suite runs SQLite, which
  reports no `varchar` length and enforces no index key limit, so widths and InnoDB's 3072-byte
  index budget are verifiable here or nowhere. Exit `0` verified, `1` a check failed, `2` the
  driver cannot answer (SQLite deployments). Already added to `DEPLOYMENT.md`'s runbook after
  `migrate --force`.
- **Rebuild assets and clear compiled views: `npm run build && php artisan view:clear`.** This
  release adds `resources/js/char-counter.js` and `resources/js/http-errors.js`, and changes the
  Blade partial behind the upload form's metadata panel. A stale build or a cached compiled view
  keeps serving the old markup after the code is correct. `DEPLOYMENT.md`'s runbook does both; a
  manual pull does not.
- **Duplicate uploads made while v1.7.0 was live are still in the database.** Ticking "Keep
  original filename" disabled duplicate detection entirely, so the same bytes could be stored
  twice under different names. The fix prevents new ones; it does not clean up old ones.
  `php artisan assets:deduplicate` (dry-run by default) finds them — but it keeps the **oldest**
  and soft-deletes the rest, so check what already links to each row before `--force`, and note
  it uses a bare `Asset::where` with no `withTrashed()`, so its notion of a duplicate is
  narrower than the upload-time one.
- **The API's duplicate payload is richer, additively.** `POST /api/assets` now returns the same
  12 fields the web paths do, and still returns `existing_asset_url`. No consumer needs to
  change; the three original keys are unchanged.
- **Rebase any branch with a spec edit in flight.** Twelve feature specs moved version in this
  release — `asset-model` (→4), `asset-upload` (→5), `chunked-upload` (→2),
  `csv-export-import` (→2), `duplicate-detection` (→2), `error-handling` (new, 2),
  `guided-demos` (→3), `input-validation` (new, 4), `localization` (→3),
  `maintenance-commands` (→2), `reference-tags-api` (→3), `rest-api` (→3) — so a branch that
  also touched one of those `version:` lines will conflict on it. Rebasing keeps the bump;
  merging can silently take your side and leave the spec looking unbumped to the gate.
- No dependency changes; `composer install --no-dev` / `npm ci` only for the usual deploy reasons.

### Changed
- **The Pest total is now counted, closing the last documented number nothing verified.** `spec-lint`'s rule for it carried a `null` and the comment "Pest tests (not auto-countable)" for as long as the other count rules existed, and it drifted twice in that time — to two different values in four places, and the second time by a **single test**, which is the size of error no human spots in review. `countPest()` reconciles exactly against `vendor/bin/pest --list-tests`, and getting there took finding three shapes rather than one: Pest's `test()`/`it()` function API, `arch()` expectations (7, each one test), and **class-based `public function test_…` methods** (42, in the Breeze-generated `ProfileTest` and `Auth/*` files). That last group is why the first attempt reconciled to 1083 instead of 1132 — those files contain no `test(` token anywhere, so a counter looking for one reads them as empty, and 49 tests were invisible in a way that a plausible-looking total would have concealed. Datasets expand: an inline array literal is sized by top-level commas, a `dataset('name', […])` declaration is resolved by name, two chained `->with()` calls multiply, and the chain is walked so `->throws(…)->with([…])` is still seen. Deliberately **not** keyed on `->with(` alone, which was the tempting shortcut and is wrong — the suite has 26 `->with('…')` calls that are Mockery expectations and Eloquent eager-loads, not datasets, so that heuristic would have inflated the total while looking like it worked. Anything unsizable — `->with($cases)`, `->with(fn () => …)`, an unknown dataset name, a PHPUnit `#[DataProvider]` — is **named and errored on**, never absorbed as one test, exactly as `loopFactorFor()` already refuses a loop it cannot size. Carries its own fixtures, checked on every run like the E2E counter's: 15 shapes it must size and 4 it must refuse, mutation-checked by disabling the class-method branch, which fails as `spec-lint self-test: …` and names the shape rather than merely reporting a wrong number. One real bug surfaced during the build and is worth recording because the design caught it: PHP `#` comments needed blanking before the shared bracket helpers (written for JavaScript) could scan the text, and the first version was not quote-aware — the suite uses `#` as a `preg_match` delimiter and in SVG fragment ids, so seven test calls had their closing brackets eaten. It failed as "unterminated `test(`" rather than as a quietly wrong number, which is the whole argument for refusing over guessing.
- **A documented count split across a line wrap was matched by nothing.** `checkCounts()` tests each line against its rules independently, so `architecture.md`'s `(1132 tests,` / `91 files: …` — the number on one line, the qualifier that identifies it on the next — matched no rule at all. That is how the Pest total drifted there unnoticed, and fixing only the counter above would have left it unchecked in the one doc that states it that way. Each line is now also tested joined with the next, the line's own match preferred so a number cannot be reported twice. The join is restricted to a genuine **continuation** — the next line must be indented further — because joining unconditionally is wrong in a way that showed up immediately: `architecture.md`'s dependency block ends one line with a trailing version number and the next line begins the `commands:` key, so the join made that version read as a count of console commands and reported the tree as having two of them. Mutation-checked by mis-stating the wrapped total and confirming it is now named with its line number. Worth knowing for anyone writing about these rules: the entry you are reading tripped the same rule on its first draft, because quoting the glued-together text put a digit next to the word the rule matches — inside `[Unreleased]`, which is checked exactly like any other doc.
- **Masonry cards no longer clip the corners of the image.** The card carried `rounded-lg` next to `overflow-hidden`, so the radius took a bite out of all four corners of every thumbnail — in the one view whose entire purpose is the uncropped image at its own proportions. Grid and list keep their rounded cards, where the thumbnail sits in a square box and the radius trims the tile rather than the picture. Nothing pinned the radius: no spec claims it, and the browser assertion for this view checks only that a card is visible, which a clipped image is.
- **The Welcome demo hands off to the library from the Assets menu, not from the step after it.** The dashboard block ended on *Your own settings*, so the sentence announcing the crossing — "next, we will open the library itself" — fired while the reader was looking at their own profile menu, and the **Assets** item, the actual way in, had been pointed at and left behind a step earlier. Swapping the two and moving the announcing sentence onto the Assets step puts the spotlight on the door at the moment it opens. Generalised into REQ-7a rather than left as a one-off edit, because it is the kind of mistake that is invisible while writing a storyboard and obvious while walking one: the step that crosses a page boundary should be the step pointing at the way there. The browser hand-off test walked to `nav-user-menu` *by name* as "the last dashboard step" and now walks to `nav-assets` — it was the only place that ordering was pinned, which is also why the swap was safe to make.

### Fixed
- **Ticking "Keep original filename" switched duplicate detection off entirely, so the same image uploaded twice under different names became two assets.** The etag check was gated on the flag — `if (! $keepOriginalFilename && ! empty($fileData['etag']))` — and the comment above it stated the intent correctly: an intentional overwrite of an existing key is not a duplicate. But the flag is not the same thing as an overwrite. It only makes a collision *possible*, by reusing the name instead of minting a UUID. With the box ticked and a **different** filename no overwrite is happening at all, and the check was skipped anyway; the `s3_key` lookup that ran afterwards then missed, because the keys differed. Two rows, one etag, nothing reported. The two checks were in fact mutually exclusive in practice: with the flag off the key is a fresh UUID and can never collide, so only the etag check was ever live; with it on, only the key check was. There was no configuration in which both ran. **The chunked path had always been right** — `ChunkedUploadService` resolves the key collision *first* and gates on `! $existingByKey` — so the identical action on a ≥10 MB file was caught. Same user, same intent, opposite outcome, decided by nothing but file size. The fix makes the direct path do what the chunked one does: hoist the `s3_key` lookup above the etag check and gate on the collision. `keep_original_filename` is no longer consulted for dedup at all. The guard itself has to stay — on a genuine overwrite the existing row already carries the incoming etag, so without it a deliberate re-upload would be refused as a duplicate of itself. **Why it shipped, which is the part worth keeping:** the spec contradicted itself. `duplicate-detection.md`'s own Background promises exactly the broken behaviour — "the same binary content uploaded under a different name … is still recognized as the same asset" — while REQ-2 stated the skip on the flag, and `chunked-upload.md` REQ-3 stated it on the collision. Both pieces of code faithfully implemented their own spec. And nothing tested it: `grep -r keep_original_filename tests/` returned **zero hits**, so the flag was unpinned in both directions — neither this bug nor REQ-2's legitimate overwrite case had a test. `asset-upload.md` had even recorded that the overwrite branch was untested, without noticing that the branch deciding whether to *reach* it was untested too. All four combinations of the flag are now pinned, and the reported case is mutation-checked: restoring the old condition turns it red with 200 instead of 409, and leaves the other three green, which is what confirms the fix is narrow. The browser test that covers it is the only place in the suite where an etag is derived from real bytes rather than stipulated by a mock — every Pest dedup test hand-writes both sides of the comparison, so none of them could ever have caught this. Two adjacent defects found in the same trace went with it. The **REST API built its own 3-field duplicate payload** instead of using `DuplicateAssetException::formatDuplicate()`, silently violating REQ-4, so an API caller got 3 of the 12 documented fields and could not render the duplicates panel; it now spreads the shared payload **additively**, keeping `existing_asset_url`, which pre-dates `formatDuplicate()` and which `public_url` does not replace (that one stays non-null for a trashed asset where this is null) — dropping it would have been a breaking API change dressed up as a cleanup. And the **etag is a storage-representation hash, not a content hash**: a single `PutObject` returns a plain MD5 while `completeMultipartUpload` returns a composite `md5-of-md5s-N`, so identical bytes either side of the 10 MB threshold can never match, and a chunked SVG is a third flavour again because `sanitizeStoredSvg()` re-puts it. That made `duplicate-detection.md`'s claim that all three paths "perform the identical etag check" false as written. It is corrected, and the real fix — a locally computed `content_hash` column — is specified in that spec's open questions rather than attempted here, because the backfill would have to download every existing object from S3 to hash it.
- **An upload whose filename ran past 255 characters was a 500, because nothing checked the name at all.** `S3Service::uploadFile()` returns `getClientOriginalName()` verbatim as the `filename` field and the controller writes it straight into `assets.filename` — sanitising applies to the S3 *key*, never to this column — and `StoreAssetRequest` had no filename rule whatsoever. `files.*` was validated as a **file**: `max:512000` is kilobytes, so it bounded the bytes and never looked at the name. A long name therefore passed validation and MariaDB rejected the insert as SQLSTATE 22001, the same class as the over-length copyright, on a path nobody had audited. Two details make it worse than it sounds. It is **independent of `keep_original_filename`** — that flag decides whether the S3 key reuses the name or gets a UUID, while the column is written from the original either way, so capping only the keep-filename path would have left the overflow exactly where it was. And the same hole was on the **replace** path, which writes the new file's name to the same column. Both now carry `App\Rules\BoundedFilename`, a sibling of `AllowedUploadExtension` that reads its limit from `ColumnLimits` so the rule, the column and the edit form's `maxlength` cannot drift; it counts with `mb_strlen`, since MySQL counts characters and an accented filename would otherwise be refused for bytes the column does not charge it for. The chunked and tools paths already derived their cap from `ColumnLimits` and needed no change. **The width is now 500 rather than 255**, which is generous on purpose: it is far past any real filename, and it is what bounds the *derived* keys. `S3Service` builds `thumbnails/L/{folder}/{basename}.{ext}` into `resize_l_s3_key`, longer than the `s3_key` it derives from; at the deepest legal folder nesting (255 + 1 + 100 = 356) and a filename at 500, the longest key the app can construct is roughly 871 characters — inside `s3_key`'s 1024, with the arithmetic itself now asserted in a test so that raising either cap without redoing it fails rather than silently reopening the overflow. `upload_sessions.filename` was widened with it: `ChunkedUploadController::initiate` validates against `assets.filename` and parks the name there until `complete()` creates the asset, so a name that column accepts has to survive the round trip. Unlike the `s3_key` widening this needed no index choreography — `assets.filename` carries `assets_filename_index`, but 500 utf8mb4 characters is 2000 bytes, inside InnoDB's 3072-byte key limit, and `db:verify-schema` re-checks that against the live server. The rejection test was mutation-checked by removing the rule: without it the request returns **200**, because the write only fails at a driver SQLite does not have.
- **An S3 key longer than 255 characters could not be stored, though S3 accepts 1024.** Every column holding an object key — `assets.s3_key`, `thumbnail_s3_key`, the three `resize_*_s3_key`, and `upload_sessions.s3_key` — was a bare `$table->string(...)`, Laravel's implicit `varchar(255)`. S3's limit is 1024 **bytes**, so the schema was refusing keys S3 itself is happy with, and reachable ones: `folder` is capped at 100 and `filename` at 255, so an upload with `keep_original_filename` composes a ~356-character key, and the *derived* keys are longer than the key they come from (`thumbnails/L/{folder}/{basename}.{ext}`). Under MariaDB strict mode that write is SQLSTATE 22001. `input-validation.md` had already recorded it as an open question — "the derived-key budget is unbounded" — and the previous release narrowed the REST API's `s3_key` rule *down* from 1024 to 255 to match the column, which treated the symptom: the column was the thing that was wrong. Since a UTF-8 key of 1024 bytes is at most 1024 characters, `varchar(1024)` holds exactly what S3 will accept. **What made this more than a one-line widening** is that `assets.s3_key` was indexed twice — its own `UNIQUE`, and the composite `assets_folder_filter_index (deleted_at, s3_key, updated_at)`. At utf8mb4 a 1024-character column is 4096 bytes, well past InnoDB's 3072-byte index key limit, so both indexes would have failed with errno 1071 — and SQLite (ADR-008) enforces neither varchar widths nor index key lengths, so CI would have gone green and the failure would have landed on the first real deploy. That is the same blind spot that let the original copyright bug live for seven months. So uniqueness moved to `assets.s3_key_hash`, a `char(64)` sha256 surrogate maintained by a `saving` hook on `Asset` — deliberately not a MySQL `STORED` generated column, because SQLite has no `SHA2()` and the suite would then be exercising an invariant production does not have. Both `s3_key` indexes are rebuilt at a **255-character prefix**: not a compromise but the status quo, since the column *is* 255 today, so the prefix has exactly the discriminating power and exactly the byte cost of the index it replaces, and the `LIKE 'folder/%'` predicate it exists for can never exceed ~101 characters because `folder` is capped at 100. A standalone `assets_s3_key_index` was added alongside, because the dropped `UNIQUE` was also the only index serving exact-match lookups on `s3_key` — six call sites, including the public `/api/assets/meta` lookup and the upload dedup check — and the composite cannot serve them, since it starts with `deleted_at`. A prefix index serves them correctly: MySQL narrows to the matching range then re-reads the full column from the row, so a false positive is impossible by construction. **Four orderings in the two migrations are load-bearing**, and each is commented where it lives. The hash's unique index is created *before* the old one is dropped, so there is never an instant without an enforced invariant. The column is added nullable and only made `NOT NULL` after the backfill, since neither a defaultless `NOT NULL` column nor a `UNIQUE` over a half-filled one is possible on a populated table. The index drops sit in the *same closure* as the `->change()` calls and are declared *first* — MySQL needs them before the widen, and SQLite's table rebuild only forgets an index once `BlueprintState` has seen its drop command. And the backfill uses `DB::table` with `chunkById`, not `Asset` with `chunk`: the `SoftDeletes` scope would skip trashed rows, whose keys are still occupied and still matched by the `withTrashed()` dedup check, leaving a `NULL` that aborts the `NOT NULL` step *after* the indexes are already gone; and offset paging would skip rows, because the loop writes the very column the `WHERE` filters on. The split into two files is not cosmetic — MySQL DDL is not transactional, so a failure in the second must not cost a second full pass over the table. **One consequence worth knowing:** a duplicate now violates `assets_s3_key_hash_unique`, and both drivers name the surrogate — MySQL through the index name, SQLite through the qualified column. `s3_key_hash` is a *real* column, so the existing `Schema::hasColumn()` guard would have accepted it and keyed the error bag on a field no form has, showing the user nothing; `DatabaseError::COLUMN_ALIASES` maps it back to `s3_key` at the point both driver paths converge. The tempting alternative — naming the new index `assets_s3_key_unique` so the existing derivation returns the right column for free — fixes MySQL and does nothing on SQLite, so it would have looked green in CI while being half broken. Also fixed in passing: `ColumnLimits` never declared the three `resize_*_s3_key` columns or the `upload_sessions` table at all, so `ColumnLimits::for()` threw for four of the six columns this change touches; and `DiscoverController` validated imported keys with `required|string` and no length cap whatsoever before writing them straight into `s3_key`. Two things are **deliberately recorded rather than fixed**: `ORDER BY s3_key` (the `s3key_asc`/`s3key_desc` sorts) is a filesort now, because no prefix index can order by a value it does not fully store; and uniqueness now depends on Eloquent events, so a raw `DB::table('assets')->insert()` could write a duplicate — there are no such call sites in `app/`, but nothing enforces that yet. Neither the 1024 widths nor the prefix-index arithmetic can be verified by the suite, so both are written up as manual MariaDB checks in `input-validation.md`, alongside a `row_format` check: nothing in the repo pins `DYNAMIC`, and five `varchar(1024)` columns under `COMPACT` would fail with errno 1118.
- **The two widenings above are unverifiable from CI, so `php artisan db:verify-schema` verifies them instead.** Not a feature — the fixes are incomplete without it. Both left assertions the suite structurally cannot make: tests run in-memory SQLite (ADR-008), which reports a bare `varchar` with no length and enforces no index key limit, so an insert MariaDB rejects with SQLSTATE 22001 succeeds in every test and an index MariaDB refuses with errno 1071 is created happily. That blind spot is the *reason* `assets.copyright` sat at `varchar(255)` behind rules allowing 500 for seven months, and shipping two more widenings behind it — one of them restructuring three indexes — would have meant taking on trust exactly what went wrong last time. The residue landed in the specs as manual "run these by hand after migrating" steps, and a checklist in a document is one nobody runs. So it is a command: it reads `information_schema` and compares the live schema against what the application believes — every `ColumnLimits::CHARS` width, every `TEXT_BYTES` capacity, the row format (`DYNAMIC`, or both the index limit and the maximum row size collapse and five `varchar(1024)` columns fail with errno 1118), and the byte size of every non-`PRIMARY` B-tree index against InnoDB's 3072-byte key limit — FULLTEXT and SPATIAL are exempt from that limit and are listed as such rather than dropped, since an unreported exemption reads exactly like a check that passed. (The first real run proved the point in both directions: it confirmed `s3_key varchar(1024)`, `filename varchar(500)`, `DYNAMIC` row format and the prefix indexes at exactly the 1020/1030 bytes the spec predicted, and it failed on `assets_fulltext` — a bug in the command, not the schema, since measuring an inverted index meant summing two TEXT columns to a meaningless 131072.) **The index check is deliberately generic** rather than a list of the indexes this change happens to touch — those are already pinned by name in `S3KeyWidthTest`, which SQLite can run. What SQLite cannot do is add up the bytes, so measuring *every* index is what tells the next person to widen an indexed column before they meet errno 1071 in production, rather than re-catching the instance already fixed. **The exit code is three-valued on purpose:** `0` verified, `1` a check failed, `2` the driver cannot answer. Collapsing `2` into `0` would let a run that verified nothing read as a pass — precisely the failure this exists to remove; collapsing it into `1` would make a SQLite deployment, supported per `DEPLOYMENT.md`, look broken. On SQLite it prints why it cannot help rather than a row of green ticks. Wired into the deploy runbook immediately after `migrate --force`. Most of it cannot be tested here for the same reason it exists, and that is stated rather than papered over; what *is* tested is the refusal to return success on an unverifiable driver, and the byte arithmetic, which is pure and is the one part that can be wrong quietly — a bad multiplier prints a comfortable number for an index the server will reject. That arithmetic independently reproduces the 1030 bytes documented for `assets_folder_filter_index`, so the migration docblock, the spec and the command now cross-check each other. It also caught a real error in the numbers written for this change: `DATETIME` is 5 bytes in MySQL 5.6.4+, not 8.
- **The upload page's copyright fields still truncated in silence — the counters landed on the edit form only.** The over-length-copyright fix established the rule as [`input-validation.md`](specs/features/input-validation.md) REQ-7 — a `maxlength` alone is not feedback, so every field carrying one gets a live counter — and then satisfied it in `assets/edit.blade.php` while `partials/upload-metadata.blade.php` got the `ColumnLimits`-driven `maxlength` and no counter. So the batch metadata panel on `/assets/create` reproduced the original complaint exactly: paste a long copyright, watch the browser cut it at 500, and see nothing on screen say so. The partial is shared, so the same silence was on `/tools/gif-maker` and `/tools/tikz-server` too, and one edit fixes all three. Nothing new was needed — `<x-char-counter>` and `resources/js/char-counter.js` already existed and are unchanged; the reason the counters were absent is smaller and easier to miss than a missing feature: the two inputs carry a `data-testid` but **no `id`**, and the component binds by `getElementById`. Giving them ids (reusing the testid values verbatim, so the counter's derived testid stays in the partial's naming) is the whole mechanism. The inputs are `x-model`-bound, which turns out to need no special handling in either direction: Alpine writes on the same `input` event the counter listens to, so typing and pasting repaint, and the panel's `x-show`/`x-collapse` only toggles `display`, so the fields are in the DOM when the counter wires itself at `DOMContentLoaded`. The one hazard is recorded in the view rather than left to be rediscovered — nothing in `uploadMetadata()` assigns those two properties programmatically today, and anything that starts to must dispatch `input` or the count goes stale. **Why the existing guards did not catch it:** `ValidationLimitsTest` reflects over the rules and scans controller source, and by design reads no Blade at all, so a view that renders a `maxlength` with no counter is invisible to it — the audit answers "does a rule outrun its column", not "does the form say so". A Feature test now asserts `GET /assets/create` renders both counters with the limit taken from `ColumnLimits`, which is the cheap check CI always runs, and a browser assertion in `upload-metadata.spec.js` fills the field to the full width and reads `500 / 500` back off the counter, which is the one that proves the JS is actually wired through Alpine. Deliberately left alone: the batch tag input and the new-folder input on the upload page also have server-side caps with no counter, but their caps are not column-backed and are out of REQ-7's scope — worth doing, not worth smuggling in here.
- **A copyright between 256 and 500 characters returned a bare 500 with no indication of what was wrong.** `assets.copyright` and `assets.copyright_source` shipped as `varchar(255)`, but *every* rule guarding them allowed 500 — `UpdateAssetRequest`, the shared upload-metadata rules, and a hand-copied duplicate of those rules inside `ChunkedUploadController::complete` — and both inputs carried `maxlength="500"`. So the value passed validation and MariaDB rejected it (`strict => true`) as SQLSTATE 22001, which nothing in the app handled: `withExceptions()` in `bootstrap/app.php` was empty and there was no `QueryException` handler anywhere. The user got "Something went wrong on our end" and no way to report it. The columns are widened to the 500 the UI, the specs and four tests already promised, rather than the rules narrowed — `copyright_source` is labelled "URL or reference", where 255 is genuinely too tight. Two things stand behind that so the class of bug cannot come back. **Prevention:** `App\Support\ColumnLimits` is now the one place a varchar width is declared, read by the migration, by every rule, and by every `maxlength=`; `tests/Feature/ValidationLimitsTest.php` asserts no character-capped rule outruns its column, fails when a new capped string field is neither mapped nor explained, checks its own allowlist for staleness, and scans controllers for a hand-written cap on a column-backed field. That audit has to introspect the *rules* rather than write to the database, because the suite runs SQLite (ADR-008), which does not enforce varchar length — the offending write succeeds in every test and in CI, which is exactly why nothing caught this for seven months. It is type-aware, since Laravel's `max` counts characters with `string`, elements with `array`, kilobytes with `file` and a ceiling with `integer`; a blanket scan would have compared a 500MB upload cap against a column width. Mutation-checked by loosening the copyright rule to 900 and confirming the failure names both the field and the fix. **Backstop:** a `QueryException` is now classified from `errorInfo` (never `getMessage()`, whose Laravel tail embeds the bindings substituted into the SQL) and turned into the keyed validation error it should have been — a 422 for JSON, a redirect-back-with-errors for a form post, produced by re-entering Laravel's own `invalid()`, so a driver rejection is indistinguishable from a rule rejection down to the body shape and the rendered `@error` block. That required amending ADR-010, which explicitly rejected a global handler: its reasoning holds for *service* failures, but a driver rejection is thrown by Eloquent inside the controller's own frame with no service to swallow it, and ADR-016 answers both of its stated objections rather than setting them aside. Unique, not-null, foreign-key, deadlock and connection failures gained actionable messages too. There is deliberately **no** catch-all `Throwable` renderer, and an unclassified DB error declines to render under `app.debug` so local debugging keeps its stack trace. Every error response now carries a six-character reference on the log line, an `X-Orca-Error-Id` header, the 500 page and a 5xx JSON body, so a user has something to quote. Four adjacent instances of the same class went with it: CSV import validated no lengths at all (a long cell 500'd the whole import naming no row, and an over-length tag name was silently *dropped* by `TagInputParser` while the row reported as updated); a tag creatable at `Tag::MAX_NAME_LENGTH` could never be renamed, because the rename rule capped at 50 and rejected the tag's own current name; the API advertised `s3_key` up to 1024 against a `varchar(255)` column; and `folder` accepted 255 where `FolderController` only ever creates 100. Client-side, `resources/js/http-errors.js` now resolves a failed fetch to the server's message — a dozen handlers, including the grid's inline licence editor on the very route that 500'd, read `errorData.message`, threw it, and then toasted a hardcoded string from the catch instead — and the two inline `window.showToast` copies in the layouts are gone, since both interpolated into `innerHTML` and were dead only because `@vite`'s deferred module happened to overwrite them. A live character counter sits under each capped field, because `maxlength` alone is not feedback: it stops accepting keystrokes in silence, which is half of why the original report said there was no indication of what was wrong.
- **`Enter` stopped stepping the guided demo the moment it crossed to another page.** Stepping with the keyboard worked same-page only *by accident*: clicking Next leaves that button focused, and the button node survives every same-page transition — only the text and the geometry change — so the next `Enter` re-activated the same node. A hand-off, though, is a full document load (`navigateTo` → `location.assign`), which resets focus to the body, so from `/assets` and `/assets/create` onward `Enter` did nothing and the reader had to find the button with `Tab` first. There was no `.focus()` call anywhere in the overlay, despite the popover having declared `role="dialog" aria-modal="true"` from the start — a contract that already promises focus moves *into* the dialog, so this was an accessibility gap wearing a keyboard-shortcut costume. `focusPrimary()` hangs off the single `requestAnimationFrame` funnel in `schedule()`, which is where every path to a rendered step already converges — anchored, unanchored, the hand-off card, the centered fallback, and `reposition()`'s own error branch — so one call site covers every way a step can come up, and it reads `settled` (just written by `reposition()`) so it cannot fire while a target is still resolving. Three decisions carry the design. It latches **once per document** rather than per step, because `schedule()` also runs on every scroll, resize and observer tick, and re-grabbing there would fight the reader for the keyboard. An **act-to-advance step consumes the latch without taking focus**: the search step asks the reader to type into the app's own input, so taking the keyboard would break the one step it was meant to help — and consuming the latch (rather than skipping it) is what stops the engine yanking focus back a step or two later. And `Enter` is deliberately **not** handled in `onKey`, which was the obvious-looking fix and is wrong: a native `<button>` already activates on `Enter`, while `onKey`'s guard tests the active element's tag — `input`/`textarea`/`select` — so a focused `button` does not read as "typing" and an explicit branch would double-fire alongside the native click, advancing two steps per press. Mutation-checked in both directions rather than trusted green: dropping the `awaiting` guard turns the act-to-advance assertion red, and dropping the `focusPrimary()` call turns both hand-off assertions red. Pinned by assertions added to the existing browser tests, so no counted total moved.
- **The guided demo told readers to pin tags, and tag pinning has never existed.** The tag-filter step said "search the tags, sort them, **pin** the ones you use constantly", and there is no such feature anywhere: no column, no pivot, no per-user store, no pin affordance in the filter panel or on the tag management page. What made it plausible is an internal name — `assetGrid.pinnedTags` is the *checked* tags hoisted above the list for the duration of the current selection, derived entirely from the checkboxes and the URL query string. So a newcomer following the one part of the app that exists to show them where things are went hunting for a pin button on a panel that has none. Two claims next door were wrong in the same direction: the masonry step sold "nothing is cropped here, every image keeps its own proportions" as that view's distinction, when the fit toggle is `x-show="viewMode !== 'masonry'"` and therefore live in grid *and* list, where `contain` keeps proportions just as well — masonry's real distinction is that there is nothing to toggle and the tile itself takes the image's shape, so it is retitled for what it is good for (visual search) instead of for a property three views share. And the sort step recommended sorting by name flatly, advice that only pays off once a filter has already cut the list down. The pin clause is replaced by the two controls the copy never mentioned — the tag-source filter and the per-tag `user`/`ai`/`ref` badge — so the step now names only things that are on screen, with the reference-tag sentence taken from the spec that owns them rather than from the badge label. **Why nothing caught it** is the part worth keeping: `GuidedDemoTest` proves every step's `target` resolves to a `data-testid` some Blade view renders and every `routeName` exists, and the browser suite steps the whole demo end to end — but nothing anywhere reads a step's `body`. A sentence is the one part of a demo with no verifier, now recorded as such in the spec's open questions and as a gotcha in the recipe, beside "don't hardcode a step count".

### Changed
- **A spec's `version:` is now enforced, because for 47 specs it was a comment nothing checked.** The rule existed in exactly one place — an inline `# bump when the contract changes` in `specs/features/_feature-template.md`. It was absent from `specs/README.md` (which documents `status:` transitions in detail), from `CLAUDE.md`, and from the `/feature` `/fix` `/spec` flows; `spec-lint` checked only that the value was a positive integer and, per its own comment, treated even that as "a warning, not a failure", while a spec with no `version:` key at all passed silently; and `sdd-guard.mjs` had no version logic whatsoever. Deliberately **not** added to the PreToolUse hook: that fires *before* an edit lands, so the bump cannot exist yet and gating there would deny the first edit to every spec. `spec-lint` now requires the key on every feature spec and errors on a non-integer, so the gate cannot be switched off by deleting it. Mutation-checked in both directions — a changed REQ with no bump fails and names the spec, the same edit with a bump passes, a scenario-only edit passes, a brand-new spec passes, and `.sdd-skip` bypasses. Two scope limits are recorded rather than papered over: `recipes/` carry a `version:` but have no contract section for the rule to read, and ADRs carry none at all.
- **The SDD Stop backstop silently missed unstaged production edits — the normal case for an agent.** `git()` trims its output and `changedProductionWorkingTree()` stripped the two status columns of `git status --porcelain` with `slice(3)`. The trim removed that space, `slice(3)` then removed the first character of the path, and the guard tested `"pp/Models/Asset.php"` against its gated prefixes — which matches nothing. So whenever the alphabetically-first changed file was merely modified rather than staged, its entry was mangled; if that was the only production file, the hook let the turn finish with no spec at all. Not a subtle edge: agents edit files without staging them, so the local backstop was unreliable rather than imperfect. CI was unaffected — it diffs `base...HEAD` by name and never parses porcelain, which is why the rule still held on PRs and this survived. Found by isolation-testing the spec-before-code rule after the version gate was added: with only `app/Models/Asset.php` modified and no spec touched, `stop` exited 0 and printed nothing. `git()` gains a `raw` option and porcelain parsing moves into one `porcelainPaths()` helper that reads the untrimmed output with an explicit column prefix; the new `unbumpedSpecs()` had inherited the same `slice(3)` idiom and now shares the helper. Verified against a base with no spec history: modified-but-unstaged production code with no spec now exits 2 and names the file, a touched spec passes, and `.sdd-skip` still bypasses.
- **Fixed a silent fail-open in the SDD guard's base-ref resolution, found while building the above.** `baseRef()` unconditionally prefixed `origin/`, which is right for `GITHUB_BASE_REF` (a bare branch name) but turned any value that was *already* a full ref into one that does not exist — `BASE_REF=v1.5.0` became `origin/v1.5.0`. Every caller then diffed against nothing, found no changes, and printed **OK**: a typo'd or mis-set base made the whole spec-before-code gate pass silently, which is the one failure mode a gate must not have. The ref is now resolved as given first and falls back to the remote-tracking form, callers receive `null` instead of a plausible-looking string, and when there is genuinely no base (a shallow clone, no remote) the CI modes print an explicit `SKIPPED — no base ref` line. Every security test in the repo asserted something a person had chosen to check — `AssetPolicyTest` covers the thirteen abilities its dataset names, `SecurityRemediationTest` the three route names it names, `role-matrix.spec.js` a fixed path list, and ~40 hand-written `'guests cannot …'` tests one route each. Nothing enumerated the application, so a route nobody wrote a test for looked exactly like a route that was safe. The new `Security` suite (68 tests, `tests/Security/`, its own PHPUnit suite and its own required CI job so a security failure doesn't read as "some test failed") derives its coverage from the router, the policy classes and the source tree, and writes down only the **exceptions** — each allowlist entry carrying a reason, each paired with a staleness check. New attack surface therefore fails CI until a human edits a list, which turns "someone should have noticed" into a required review step. It audits: every route is authenticated, guest-only or allowlisted-public (plus a live unauthenticated sweep of every parameter-less guarded `GET`, because declared middleware proves configuration, not behaviour); every rate limit on every unauthenticated route; no registration surface under **any** name; every policy ability has a stated verdict for every role, discovered by reflection, with no `return true`, no `before()` hook and no `Gate::before()`, cross-checked against the roles the `users.role` constraint permits; every controller behind `auth` gates its routes, gates itself, or is declared open to all roles; every user-creation idiom names a role; no model write takes an unfiltered `$request->all()`; every encrypted `User` attribute is also `$hidden`; and 21 live probes drive editor/api/admin/guest against the real endpoints. Four **canaries** are permanent tests rather than a manual checklist — they mount an unguarded route, an ungated controller, a `return true` ability and an unroled creation, and require each audit to name it, because an audit that has silently stopped matching produces the same green tick as a clean codebase. Two findings came out of writing it: `DatabaseSeeder` created its user through `User::factory()->create()` with **no role**, taking the factory's `editor` default on a path `php artisan db:seed` can reach in production — invisible to `RegistrationTest`, which scans `app/` only and matches only the literal `User::create(` — now explicit; and `Route::resource('users')` carried no route-level gate despite the "admin only" comment, resting entirely on seven in-controller `authorize()` calls, so a new method added without one would have been reachable by any editor session — now gated at both layers like `system/*` already was. `composer audit --locked` and `npm audit` join the same job (both clean, so no ignore list): the first dependency scanning this repo has had. Spec: [`specs/features/security-invariants.md`](specs/features/security-invariants.md).
- **The two runtime settings that open API surface are now tested on both sides of their branch.** `api_meta_endpoint_enabled` and `api_upload_enabled` live in the database and are flipped from `/api-docs`, so whether an *unauthenticated* metadata endpoint is open is operator state, not code — nothing in a diff reveals it, and `specs/features/rest-api.md` recorded both branches as having no coverage anywhere under `tests/`. Both states of both settings are now asserted: the metadata kill switch withholds the data rather than merely changing the status line, and closes the endpoint for authenticated callers too (the check precedes any auth consideration, so a refactor that moved it behind an auth branch would leave the endpoint open to every token holder while the setting read "off"); disabling uploads stores nothing, asserted with no S3 mock so a leaking gate fails loudly instead of recording a success against a stub. Only an admin can flip either. The toggle set is read from `ApiDocsController::updateSettings`'s own validation rule, so a **new** runtime toggle fails the suite until both of its states are covered. That closed finding is removed from `rest-api.md`'s open questions rather than left to rot.
- **Dropped the `users.role` database default of `editor`.** Removing `/register` closed the route that exploited the default, but the default itself — the mechanism that turned an omitted `role` into full asset read/write — was still there for the next creation path to fall into. `users.role` is now `NOT NULL` with no default (`database/migrations/2026_07_30_120000_drop_role_default_from_users_table.php`), so an insert that omits the role fails at the driver (`NOT NULL constraint failed` on SQLite, `Field 'role' doesn't have a default value` on MySQL/MariaDB under `strict`) instead of silently minting an editor. This covers paths the `RegistrationTest` source scan cannot see — `firstOrCreate`, raw inserts, a future SSO or invite flow. No caller changes: `UserController::store` validates `role`, `TokenController::store` and `TokenCreateCommand` hardcode `api`, `UserFactory` sets `editor`. **The migration aborts rather than backfilling if any row holds a `NULL` role** — every role grants strictly more than `NULL` does, so an operator assigns those roles. Pinned by a new scenario in `specs/features/authentication.md` REQ-8; the SQLite path recreates the table from its own stored DDL because `2026_01_26_111545`'s hand-written `email … UNIQUE` left an implicit `sqlite_autoindex_users_1` that Laravel's `->change()` cannot replay.

### Security
- **Removed self-service registration — it granted `editor` to anyone who found the URL.** The Breeze `register` route shipped mounted but unlinked from the navigation, and `RegisteredUserController::store` passed no `role` to `User::create`, so a self-registered account took the `users.role` column default of `editor` — view, create, update, replace, soft-delete, restore and bulk-download over the **entire** asset library. Because email verification is inert (`User` does not implement `MustVerifyEmail`), that access was live from the moment of signup with no confirmation step. Unlinked is not unreachable: an unknown party had registered on production. The route, `RegisteredUserController` and the register Blade view are deleted, so both verbs now `404`; `tests/Feature/Auth/RegistrationTest.php` inverts to pin their absence and additionally asserts no `User::create` call site under `app/` leans on the column default. - **New user audit trail (`user_audit_logs`) + `php artisan users:audit`.** A `users` row recorded when it was created but nothing about an `UPDATE` that flipped `role`, so the most security-relevant mutation in the system was invisible after the fact — the self-registered `editor` account above was found by a human noticing an unfamiliar name, and a later escalation to `admin` would have left no trace at all. A `UserObserver` now appends who created, re-roled, renamed, re-addressed or deleted an account, and who did it (`actor_id`, plus an `actor_label` that survives the actor's own deletion; `console` for CLI provisioning). Watched attributes are an allowlist — `role`, `email`, `name` — so logins, password changes and 2FA columns file nothing and cannot leak a secret into the trail. Granting `admin` additionally emits a `warning` to the application log. The trail is append-only, and an audit write that fails is logged rather than allowed to break the operation it was auditing. No UI yet: `users:audit --user= --event= --limit=` is how you read it.
- **Password reset no longer confirms whether an address has an account, and is rate-limited.** `POST /forgot-password` reported the broker status verbatim, so `passwords.user` ("We can't find a user with that email address") made the endpoint a login-name oracle for any unauthenticated caller; `passwords.throttled` leaked the same fact more quietly. It now returns one generic confirmation for every syntactically valid address, and logs the non-sent outcomes server-side so operators keep the signal. All four `/forgot-password` + `/reset-password` routes gained `throttle:6,1` — the broker's own 60s `auth.passwords.users.throttle` only debounces repeat links to the *same* address, so it did nothing against a caller walking a list. `POST /reset-password` still reports failures verbatim: it needs a valid signed token, so it tells a caller nothing they don't already know. - **API asset replace ignored the `replace` policy ability, and API update silently dropped fields.** `AssetReplaceController` never authorized `replace`, so an `api`-role token could overwrite an asset's bytes even though the role is not granted that ability — it now returns `403`. Non-inline types are stored with `Content-Disposition: attachment`, and the download endpoint sends `nosniff` + RFC-5987-encoded filenames.
- **Baseline security headers.** New `SecurityHeaders` middleware on the web group adds `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN` (relaxed by `AllowEmbedding` when embedding is configured), `Referrer-Policy`, and HSTS over HTTPS. `SESSION_SECURE_COOKIE` now defaults to `true` in production.
- **CSV export formula-injection** neutralized — `CsvExportService` prefixes cells starting with `= + - @` tab/CR with `'`.
- **Rate limits** on expensive/public endpoints (TikZ render, AI tagging, bulk download, public `/api/assets/meta` + `/api/health`, the `/api/assets` group).
- **Reduced info disclosure** — API-role users receive generic error messages (admin/editor still see detail); `embed_allowed_domains` is validated before composing the CSP; `bulkGetTags` now authorizes per asset; the TikZ blocklist rejects all file-inclusion commands.
